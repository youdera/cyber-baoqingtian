# 官网访问失败原因核验

本机核验时间：2026-09-13 00:01—00:07（北京时间）。对照同一网络、同一官方 robots 地址、同一 User-Agent 的 Python Requests/OpenSSL 与 Windows curl/Schannel；没有更换代理线路、关闭证书验证或跟随被阻止的目录。

## 结论

失败不是一种原因。已证实有 TLS 客户端兼容差异，也有访问拒绝、反爬校验和官网目录分页问题。不能把失败统称为“网络不好”，也不能根据一次失败认为网站永久不可用。

| --- | --- | --- | --- |
| 深圳市人社局 | robots 阶段 BAD_ECPOINT | robots 返回404 | 改用标准 P-256 曲线重试后，现有 Fetcher 读取到真实门户和公开招录目录 |

| 重庆人社局 | robots 阶段 HTTP403 | 同样HTTP403 | 无权据此判断具体公告页；保留失败，未越过访问规则 |

| 上海拟聘目录标示末页 | 目录 index_321/index_322 返回404，较早页可读 | 未重复比较 | 属于实际分页与导航不一致，保留历史缺口 |

robots 返回404只说明没有在该路径提供规则；不能单凭它认定公告目录可读。深圳、湖南另行验证了真实目录内容才接入。

本机启用了 FlClash 隧道，解析结果使用其虚拟地址。本轮未核验各站点实际使用的直连/代理规则，也未切换网络做同步对照，因此**不能认定代理就是根因**。同一网络更换 TLS 客户端即成功，足以证实部分问题与 TLS 协商方式有关；这不排除网络路径或网站设备参与其中。

## 兼容修复

Fetcher 仅对明确的 `BAD_ECPOINT` 错误重试一次，采用标准 `prime256v1`（P-256）曲线。继续使用 `ssl.create_default_context()`，证书链、主机名验证与最低TLS版本保持开启；没有开启旧式重协商、忽略证书或针对403/验证码进行绕行。[Python SSL 官方说明](https://docs.python.org/3/library/ssl.html#ssl.create_default_context)

其他错误现在分别显示发生在 robots 规则请求还是公告目录请求，并区分TLS、HTTP状态、超时和连接中断。兼容成功记录为 `p256_compat`，不自动视为历史完整。
